# 采集暂停与继续（断点续采）

日期：2026-10-12（Asia/Shanghai）。用户确认的需求见交接说明第八节第 3 项；本轮用户指令是“先做暂停/续采，等这块做好，然后测试完成，再进行其他的”。本记录只覆盖这一项。

## 行为

- 采集中可点“暂停”：等待当前请求收尾，进度写入断点，按钮变为“继续”。暂停期间关键词、模式、目标条数锁定，“开始采集”不可用，Cookie 可改。
- “继续”按原任务参数从断点接着采；续采开始时助手把断点中的结果重新交给界面，列表以断点为准重建，恢复的行不逐条写日志。
- “停止”在暂停状态下表示结束该任务：清除暂停记录，列表中的结果保留，不向助手发命令。暂停请求尚在收尾时点停止，按停止结束。
- 关闭软件再打开：恢复关键词、模式、目标条数和“暂停时已采 N/M 条”的提示，按钮为“继续”；Cookie 不落盘，需重新填入。
- 风控询问是独立路径：询问期间“暂停”不可用，状态文案改为“账号受限 / 采集遇到账号限制”，不再使用“已暂停”。
- 只有主动暂停的任务可以继续。续采途中出错或助手意外退出，任务回到暂停状态；首轮出错、用户停止、未暂停直接关闭软件，按原来的方式结束。

## 实现

- 助手协议新增 `pause` 命令；`done` 事件新增 `paused`、`failed`；续采时以 `restored=true` 的 `item` 事件交还旧结果。暂停与停止共用收尾路径，暂停后再停止按停止算；暂停会放行正在等待的风控询问，但不替用户答复继续。
- 两份核心同步修改 `collect.py`、`collect_engine.py`、`checkpoint.py`，共有文件逐字节一致。
- C#：`CollectHelperClient` 增加 `PauseCollectingAsync` 与事件字段；新增 `CollectPauseStore.cs`，暂停记录保存在 `<数据目录>\collect\paused-task.json`，内容为模式、关键词、目标数、数量与时间，不含 Cookie；`CollectViewModel`、`CollectView.xaml`、`AppBootstrap.cs` 相应修改。

## 由新测试先复现、随后修复的现有缺陷

1. 关键词约 3000 个以上时，默认断点路径计算抛出 `ValueError: stat: path too long for Windows`，采集无法开始（2000 词正常，3000 词失败，系统 Python 3.12 实测）。修复后 10000 词可用，短词表的断点文件名不变。
2. 模糊补足阶段：页标记在请求之前写入，恢复时遇到某条查询第 1 页已做过就整条跳过，剩余页丢失；被打断的页也被当作已完成。现增加每条查询的翻页位置（`query_cursor`），被打断的页撤销标记后重做，查询翻完或连续无新增结束时写完成标记。
3. 精准模式：恢复后已处理的未命中词不再补量；暂停点落在补量阶段时，继续后立即结束。现改为未命中的词仍补量，并用 `supplement_done` 跳过已补过的词。原契约测试 `test_resume_processed_misses_not_supplemented_…` 记录的是原版 v1.0.4 行为，已改写为“每个未命中词只补一次”，原因写在测试内。
4. 断点现在保存关键词列表，恢复时不一致则不沿用旧进度并记日志。

上述 2、3 两项只改变恢复路径；未使用恢复时的查询顺序、筛选和停止条件不变，原有 222 项助手测试除上述一条契约外全部保持通过。
